STAGE 1 — SINGLE-SOURCE PUBLIC ORIGIN

CONFIRMED DEFECT

Public origin information is currently duplicated across:

- astro.config.mjs
- src/data/site.ts
- public/robots.txt

Additional consumers include:

- src/layouts/SiteLayout.astro
- src/pages/sitemap.xml.ts
- src/pages/llms.txt.ts
- src/pages/llms-full.txt.ts
- src/pages/[locale]/llms.txt.ts
- src/pages/docs/[...slug].md.ts
- src/pages/[locale]/docs/[...slug].md.ts
- src/content-engine/i18n/catalog.ts

The configured origin is currently https://saipenprotocol.com.

A temporary deployment on a different hostname would still emit references to the permanent hostname. This is undesirable for search indexing, canonical identity, social previews, and migration.

IMPLEMENTATION

A. Establish one validated, build-time source for the public origin.

Use a small shared Node-compatible deployment configuration module. Both Astro configuration and server-side static rendering must consume it.

Prefer an explicit environment variable such as SAI_SITE_ORIGIN.

Requirements:

- Accept an absolute HTTPS origin for public release builds.
- Reject credentials, query strings, fragments, unsupported protocols, invalid hostnames, and unsupported path-based deployment.
- Normalize harmless trailing-slash differences.
- Keep deterministic local development and CI defaults.
- Require explicit origin acknowledgement for a production-release verification.
- Never silently assume that the permanent domain is reachable.
- Do not use a runtime browser dependency for origin resolution.

Preserve the distinction between:
1. Planned permanent domain.
2. Effective deployment origin.

The former may remain editorial information. The latter must control emitted URLs.

B. Remove duplicated origin authority.

Use the shared origin for:

- Astro site configuration
- Canonical links
- Open Graph URLs and images
- hreflang and x-default URLs
- Sitemap entries
- robots.txt sitemap reference
- llms.txt and llms-full.txt references
- Localized documentation references
- Relevant release metadata

For robots.txt, replace the fixed public asset with a generated Astro endpoint if that is the cleanest solution.

Avoid parallel public/robots.txt and generated robots routes.

C. Preserve existing root-relative navigation.

Do not change internal links to absolute public-origin URLs unnecessarily.

D. Ensure origin configuration is consistent within a single build.

No output artifact may mix the temporary and permanent hostname unless explicitly intended as editorial content or an upstream source link.

STAGE 2 — INDEXING AND INTERNAL ROUTE HARDENING

CONFIRMED DEFECT

The five diagnostic pages under src/pages/debug/ use SiteLayout without an explicit noindex property.

SiteLayout currently defaults noindex according to locale state and publication readiness, not the debug route category.

robots.txt disallows /debug/, but this alone does not provide a complete indexing exclusion contract.

TARGET FILES

- src/layouts/SiteLayout.astro
- src/pages/debug/components.astro
- src/pages/debug/content.astro
- src/pages/debug/fonts.astro
- src/pages/debug/rendering.astro
- src/pages/debug/themes.astro
- public/robots.txt or its generated replacement
- src/pages/sitemap.xml.ts

IMPLEMENTATION

A. Make debug-route indexing exclusion a shell-level invariant.

Do not depend on every future debug page author remembering to set noindex manually.

B. Preserve exclusions for:

- Internal pseudo-locales
- Unapproved translations
- Alias and redirect pages
- Other explicitly nonpublic routes

C. Preserve public canonical URLs for eligible pages.

D. Avoid putting internal or debug routes into the public sitemap or public hreflang output.

E. Add negative controls proving that introducing a new debug route cannot accidentally make it indexable.

F. A noindex rule is not authentication.

Keep the existing distinction between internal diagnostics and genuinely private information. Never ship secrets or internal project-memory files in dist/.

STAGE 3 — RELEASE PREFLIGHT

Current site:doctor HEALTHY means the local content and declared contracts are consistent. It does not establish public deployment readiness.

Add a focused release preflight rather than weakening or overloading the existing content health contract.

Suggested entry point:
npm run release:verify

Use a narrowly scoped script under scripts/.

It must validate the already built output and effective release configuration.

Required checks:

1. Effective public origin is explicit and valid.
2. Astro origin, SITE origin, canonical URLs, sitemap, and robots.txt agree.
3. Public sitemap entries refer to generated public routes.
4. Sitemap does not contain debug, pseudo-locale, or unapproved locale pages.
5. Debug pages carry noindex.
6. Internal pseudo-locale pages carry noindex.
7. Canonical paths resolve consistently.
8. Generated Markdown and llms references use the selected public origin.
9. No stale absolute canonical URLs remain from a previous deployment origin.
10. Only production build artifacts are eligible for deployment.
11. No project memory, evidence, credentials, temporary work packages, source scripts, or test reports are included in the publishable output.
12. Release verification produces a deterministic, machine-readable result containing the origin, package version, protocol snapshot identity, artifact identity, checks, and verdict.

Differentiate:
- PASS: locally proven release artifact contract.
- FAIL: demonstrated output or configuration defect.
- BLOCKED: operator decision or external verification unavailable.

Do not claim DNS, HTTPS accessibility, hosting compatibility, or actual search engine indexing from offline checks.

Do not add fake success results for unavailable external services.
